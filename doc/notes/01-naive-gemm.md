# 01 · 最朴素的 GEMM（三重循环）

> 对应代码：`code/src/normal.cpp`
>
> 本文目标：把上一节的概念落到第一版能跑、能量化性能的实现，并建立一个**性能基线**，后续所有优化都以此为参照。

## 1. 本节目标

很多教程一上来就讲 tiling、SIMD、寄存器缓存，但在学这些之前，我们首先要回答一个问题：**什么都不做，直接写三重循环，到底有多快？**

这一节我们要做三件事：

1. 实现最直接的 `i-j-k` 三重循环版本；
2. 用 Google Benchmark 量出它的 GFLOPS，建立第一个**性能基线**；
3. 分析朴素版本为什么慢——慢的原因，就是后面所有优化的出发点。

## 2. 朴素算法

### 2.1 核心代码

```cpp
// 注意：这里累积写入 C，等价于 beta = 1；要算 C = A * B，需先把 C 清零
for (int i = 0; i < n; i++) {
    for (int j = 0; j < n; j++) {
        for (int k = 0; k < n; k++) {
            C[i * n + j] += A[i * n + k] * B[k * n + j];
        }
    }
}
```

逐层拆解：

- **最外层 `i`**：遍历 `A` 的每一行；
- **中间层 `j`**：对当前行，遍历 `C` 的每一列（也就是 `B` 的每一列）；
- **最内层 `k`**：把 `A` 第 `i` 行的第 `k` 个元素，和 `B` 第 `j` 列的第 `k` 个元素相乘累加。

一句话：**拿 A 的一整行 × B 的一整列，点积出 C 的一个元素。**

这里最关键、也最容易被忽视的是**内存访问模式**。假设矩阵按行优先（row-major）存在连续内存里：

- `A[i * n + k]`：内层循环里 `k` 递增，地址连续，**顺序访问**；
- `C[i * n + j]`：同一行内 `j` 递增，地址也连续，**顺序访问**；
- `B[k * n + j]`：`k` 递增时地址一次跳 `n` 个元素，**跨行跳跃访问**。

::: warning 问题所在
`B[k][j]` 的访问每次跳过一整行。内层循环每算一个元素就要从内存里"跳"一次，这是朴素版本最浪费的地方，第 5 节会展开讲。
:::

### 2.2 为什么用一维数组 + 索引计算

完整代码里矩阵是用 `std::vector<double>` 的一维数组存的，访问时手动算 `i * n + j`，而不是 `double C[n][n]` 这种二维数组。原因：

1. **连续内存**：`std::vector` 保证元素在堆上连续存放，配合缓存（Cache Line）效率最高；`C[i][j]` 这种二维数组本质也是连续的，但这里用一维数组是为了显式表达"线性地址 = 行号 × 每行长度 + 列号"这个事实，后续做分块（tiling）时索引计算更清晰；
2. **尺寸可变**：`C[n][n]` 是编译期定死的，而 benchmark 要测 128/256/512 多个尺寸，运行时才知道 `n`；
3. **方便随机初始化**：`std::uniform_real_distribution` 可以一行行地给连续内存填充数据。

> 注意：`i * n + j` 这种写法是**行优先（row-major）**，也是 C/C++ 的默认习惯。Fortran 和 BLAS 传统上用列优先，这是后面和 OpenBLAS 对比时要留意的一个坑。

## 3. 复杂度分析

- 乘法次数：$M \times N \times K$
- 加法次数：$M \times N \times K$
- 总浮点运算数（FLOPs）：$2 \times M \times N \times K$

以 $n = 1024$ 的方阵为例：

$$
2 \times 1024^3 = 2,147,483,648 \approx 21.5 \text{ 亿次浮点运算}
$$

也就是说，**单单算一次 1024² 的矩阵乘法，就要执行约 20 亿次浮点运算，也就是约 10 亿次乘加（FMA）**。如果机器每秒只能做 10 亿次浮点运算（1 GFLOPS），一次乘法就要 2 秒多。

时间复杂度是 $O(n^3)$——这意味着规模翻一倍，计算量变成 8 倍。这也是为什么矩阵乘法的性能如此重要：**它是深度学习、科学计算里最核心、最耗时的算子**，n 一上万，任何优化手段带来的收益都会被放大到极其可观。

## 4. 基准测试

### 4.1 构建与运行

```bash
cd code
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
./build/normal
```

> 一定要 `Release`（`-O3`）。`-O0` 下编译器不做任何优化，测出来的数字没有参考价值。

代码里用 Google Benchmark 封装了内核：

```cpp
for (auto _ : state) {
    std::fill(C.begin(), C.end(), 0.0);  // C += A * B，每次迭代前先清零
    naive_gemm(n, A, B, C);
    benchmark::DoNotOptimize(C.data());  // 防止编译器把整个计算优化掉
}
```

- `state` 循环由框架自动控制迭代次数和预热（warmup），保证测量稳定；
- `DoNotOptimize` 告诉编译器"C 被用过了，别删"，避免死代码消除（传 `C.data()` 裸指针比传整个 `std::vector` 更贴合官方的推荐用法）；
- 用 `->Arg(128)->Arg(256)->Arg(512)` 一次测三个矩阵规模。

### 4.2 衡量指标：GFLOPS

$$
\text{GFLOPS} = \frac{2 \times M \times N \times K}{\text{运行时间（秒）}} \times 10^{-9}
$$

**为什么用 GFLOPS 而不是毫秒？**

- 毫秒只在"同一个矩阵规模"下有可比性；规模一变，耗时完全不同；
- GFLOPS 是**归一化**的吞吐量：不管矩阵多大，这个数字都代表"每秒做了多少十亿次浮点运算"，可以直接和别的实现、别的机器对比；
- 后续每做一步优化，只需要对比同一组规模的 GFLOPS 提高了多少倍。

> 对照代码：`normal.cpp` 里的计数器叫 `FLOPS`，`kIsRate` 会把它除以 CPU 时间；打印时带 SI 前缀，比如输出里的 `1.738G` 就是 1.738 GFLOPS。

### 4.3 实测结果

| 矩阵规模 | 耗时 (ms, CPU) | 吞吐 |
| --- | --- | --- |
| 128 | 2.413 | 1.738 GFLOPS |
| 256 | 29.14 | 1.152 GFLOPS |
| 512 | 350.1 | 766.8 MFLOPS |

> 测试环境：MacBook Pro 16,2（Intel Core i7-1068NG7，4 核 8 线程，2.3GHz，16GB），Apple clang 21，`-O3`。
>
> 运行方式：`./build/normal --benchmark_min_time=1s --benchmark_repetitions=5`，表中取 5 次重复的**中位数**（CV < 1%）。测量时系统有后台负载（load average ≈ 3.3，编辑器 + Spotlight 索引），绝对值会偏低，但趋势稳定可复现。

**注意一个反直觉的现象：矩阵越大，GFLOPS 反而越低**（1.738G → 1.152G → 0.767G）。

这正好印证了朴素版本的问题是**访存而不是计算**：规模增大后，数据超出各级缓存容量，CPU 越来越频繁地等内存，计算单元反而越来越闲。这就是下一节要分析的瓶颈。

::: tip 衡量一下差距
朴素版本的 0.8~1.7 GFLOPS 只是一个起点。它离这颗 CPU 的浮点上限还有多远？这里先不引用任何"理论峰值"，等后面每一步优化落地后，都用同一套 benchmark 把差距一步步量出来。
:::

## 5. 瓶颈分析

### 5.1 CPU 很闲，内存很忙

现代 CPU 的存储是金字塔结构，越往上越快、越小、越贵：

| 层级 | 容量（本机） |
| --- | --- |
| 寄存器 | 几十个 × 8 字节 |
| L1 缓存 | 48 KiB |
| L2 缓存 | 512 KiB |
| L3 缓存 | 8 MiB |
| 主内存 | 16 GiB |

（容量是这台机器的参数，benchmark 启动时会打印；延迟这里只作"越往上越快"的定性描述，不引用具体数字。）

算一次浮点乘加非常快，但**从主内存取一个数的延迟要高得多**。CPU 一次只能同时等少量内存请求，所以如果代码不停地从内存搬数据，ALU（计算单元）绝大多数时间都在空转。

这种**计算单元大部分时间都在等数据**的程序，叫做 **memory-bound（访存受限）**。朴素 GEMM 就是典型的 memory-bound。

### 5.2 三重循环的内存访问模式

缓存不是按"单个字节"搬运的，而是按 **Cache Line（通常 64 字节 = 8 个 double）** 成块加载。所以"一次取一个数"和"一次取连续的一串数"在成本上几乎一样。

回顾三个矩阵的访问模式：

- `A[i][k]`：内层 `k` 递增 → 连续读取，**每个 Cache Line 的 8 个 double 全用上** ✅
- `C[i][j]`：连续写入 ✅
- `B[k][j]`：`k` 递增时地址跳过 `n` 个元素 → **每次只用了 Cache Line 里的 1 个 double，其余 7 个全部浪费** ❌

以 n=512 为例，访问 `B` 时每取一个数，就要浪费 56 字节的带宽。B 是整个内层循环的"流量大户"，这导致：

- 内存带宽被无效读取大量消耗；
- 每访问一个 `B` 元素都伴随一次（潜在的）缓存缺失（cache miss），要等一次主内存的延迟；
- 内层循环每步都卡在等待上，向量化和多发射根本来不及发挥。

### 5.3 数据被反复从内存读取

再看 `A` 的访问：固定一行 `A[i]`，内层每算一个 `C[i][j]` 都要把这一整行（n 个元素）从头读一遍。

以 n=1024 为例：

- `A[i]` 一行 = 1024 × 8 = 8 KiB（128 个 Cache Line）；
- 这一行会被**重读 1024 次**（对应 1024 个 j），每次都是一次完整扫描；
- 但一轮 j 迭代里，`B` 还会流式经过 1024 个 Cache Line（64 KiB）。8 KiB + 64 KiB = 72 KiB 已经超过 L1 的 48 KiB，`A[i]` 会在一轮迭代中被挤出去，下一轮 j 只能退到 L2 重取——比 L1 慢，但还远没到主内存那个量级。

不过要强调的是：**A 的流量其实是次要的**。同一轮 j 迭代里，`B` 要搬 1024 个 Cache Line，`A` 只有 128 个，相差 8 倍；n=512 时更宽松（A 行 4 KiB + B 每轮 32 KiB = 36 KiB，甚至塞得进 L1）。也就是说，A 的重读顶多让 L2 忙一点，而下面这条才是真正的浪费：

- `B[k][j]` 每取 1 个元素就要搬一整条 Cache Line（64 字节），**利用率只有 1/8**，7/8 的带宽都打了水漂。

**结论：朴素版本的问题不是"算得慢"，而是"同样的数据反复从内存搬，带宽全浪费在无效访问上"——其中最贵的一项是 `B` 的 Cache Line 利用率。**

## 6. 小结与下一步

朴素版本给出了一个**很烂但很真实的基线**：约 0.8~1.7 GFLOPS。但它把问题暴露得很清楚：

| 问题 | 优化方向 |
| --- | --- |
| B 按列访问，Cache Line 利用率低 | 循环重排（如 ikj 顺序） |
| A 的行超出 L1，被反复重读 | 循环分块（Tiling），让数据留在缓存 |
| 完全没有利用向量指令 | SIMD 向量化（AVX2 / AVX-512 / NEON） |
| 只用了一个核 | 多线程（OpenMP） |

这四个方向，就是接下来每一节笔记的主题。每一步改完后，都要回到这套 benchmark，用同一组规模对比 GFLOPS——**优化的唯一标准，就是数字有没有变好**。

下一篇预告：**循环重排（ikj）**——只调整三重循环的顺序，不做任何"高深"的事，看看 GFLOPS 能提升多少。
